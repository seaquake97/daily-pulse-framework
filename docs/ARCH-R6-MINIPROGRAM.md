## 1. 目标与非目标

**目标**

- Phase 1：把已有研判内容以**只读**方式在微信内消费（首页时间线 / 日期页 / 详情页）
- 复用现有站点产物，**不重跑任何计算**
- 与 R5 框架解耦：小程序是产物的**消费者**，不是新的数据生产端

**非目标**

- 不在客户端做任何行情取数或计算（合规风险 + 与框架职责冲突）
- 不做交易、下单、跟单、荐股
- 不做持仓录入（持仓是私密的，小程序端不上传）
- 不在 Phase 1/2 做用户体系（无登录、纯只读）

## 2. 技术选型

### 2.1 方案矩阵

| 维度（权重） | A. Taro 4 | B. uni-app | C. 小程序原生 |
|-------------|-----------|-----------|-------------|
| 学习成本（20%） | 中（需 React + 小程序双栈认知） | 低（Vue 单栈，HBuilderX 全流程） | 低（无框架，但要手写 WXML/WXSS） |
| 包体积（15%） | 编译后中等，tree-shaking 好（实测可省约 30%） | 首包偏大（社区实测 8-12MB，需分包压到 2MB 内） | **最小**，零运行时 |
| 生态成熟度（20%） | 37.7k★，v4.3.0（2026-09-29 发布），持续维护 | 生态最大、插件市场最丰富、市场占有率最高 | 官方文档，能力无延迟 |
| 与本项目技术栈契合度（25%） | **高**——站点是 Python + Apple 设计语言，若未来做 H5 可共享 React 组件 | 低——团队与现站点均非 Vue 生态 | 中——共享面小，但渲染保真度最高 |
| 发布审核风险（10%） | 无差异 | 无差异 | 无差异 |
| 未来多端扩展（10%） | **高**（小程序 + H5 + RN 三端） | 高（小程序 + App + H5） | 无（仅小程序） |

**结论：选 A（Taro 4 + React）**，理由按权重排序：

1. **契合度权重最高（25%）且是决定性的**：本项目的核心资产是「Python 产内容 + 一套设计 Token」。
   选 Taro 的实际收益不在小程序本身，而在于**未来若做 H5/APP，React 组件可与站点前端共享**。
   选 uni-app 会引入 Vue 栈，与现站点的 Apple 设计语言实现（`site_*.py` + CSS）无任何共享。
2. **不为省力选 uni-app**：「学习成本低」对本项目是伪优势——真正的成本在设计语言迁移，
   而不在框架语法。
3. **不选原生**：Phase 1 只有 3 个页面，原生确实够用且包体积最小。但它把未来多端成本
   一次性推到不可逆的位置，而 Taro 的多端能力是增量收益。

**但必须诚实说明 Taro 的代价**（不做过度承诺）：

- 编译后代码体积大于原生，需要主动分包
- 部分 React 特性在两端行为不一致（如 `useEffect` 时序）
- 渲染保真度低于原生，**站点精心设计的排版在小程序里必然有降级**（§4.2）
- 社区问题响应快但学习曲线陡

### 2.2 若决策层更看重「最快上线 + 最小体积」

则选 C（原生）。3 个只读页面用原生写，工作量不大、包体积最小、渲染保真度最高，
且完全没有跨端框架的学习与调试成本。**Phase 1 用原生、Phase 2+ 再评估 Taro 也不迟**——
这是本文保留的合理选项，请在评审时明确选定，不要默认 Taro。

## 3. 架构：小程序如何消费站点产物

### 3.1 方案：站点侧产出只读 JSON feed

```
内容仓（GitHub Pages）
  docs/api/feed.json        ← 新增：时间线索引（首页用）
  docs/api/day/<date>.json  ← 新增：单日详情数据
  docs/daily/<date>/*.html  ← 已有：完整详情页（web-view 兜底用）
```

**为什么不让小程序去解析 HTML**：HTML 解析在小程序里代价高（无 DOM、正则脆弱），
且站点改版会让客户端静默失效。JSON 是显式契约，改版时 schema 版本可协商。

**为什么保留 HTML**：作为 `web-view` 兜底入口——完整排版、零重写成本，
在 JSON 渲染降级时使用（§4.3）。

### 3.2 `feed.json` schema

数据源已存在：`_stage/docs/daily/<date>/meta.json` + `entries.json`。
`build_site.py` 增加一次 `emit("docs/api/feed.json", ...)` 即可，**不需要新的上游数据**。

```json
{
  "schema_version": "1.0.0",
  "generated_at": "2026-01-02",
  "base_url": "https://<user>.github.io/<repo>/",
  "disclaimer": {
    "ai_generated": true,
    "profile": "investing",
    "notice_zh": "本文由 AI 自动生成，不构成投资建议……"
  },
  "days": [
    {
      "date": "2026-01-02",
      "title_zh": "每日总复盘 · 2026-01-02",
      "summary_zh": "Σ 评级【防守】（-0.339），覆盖 5 项任务产出，数据时点 收盘时点。",
      "rating": "防守",
      "sigma": -0.339,
      "data_stage": "close",
      "tasks": ["基金盘面分析", "股票助手"],
      "entry_count": 5,
      "degraded": false,
      "detail_json": "api/day/2026-01-02.json",
      "detail_html": "daily/2026-01-02/index.html"
    }
  ],
  "pagination": {
    "total_days": 30,
    "returned_days": 30,
    "has_more": false
  }
}
```

字段来源（全部已有，零新增采集）：

| 字段 | 来源 |
|------|------|
| `date` `title_zh` `summary_zh` `rating` `sigma` `data_stage` `tasks` | `meta.json` |
| `entry_count` `degraded` | `entries.json` 聚合 |

### 3.3 `day/<date>.json` schema

```json
{
  "schema_version": "1.0.0",
  "date": "2026-01-02",
  "rating": "防守",
  "sigma": -0.339,
  "data_stage": "close",
  "comparable": true,
  "disclaimer": { "profile": "investing", "notice_zh": "……" },
  "entries": [
    {
      "slug": "daily-review",
      "name": "每日总复盘",
      "time": "15:30",
      "title": "每日总复盘 · 2026-01-02",
      "conclusion": "防守 · Σ-0.339｜定投额度下调 ≥30%，网格买单一律暂停",
      "summary": "……",
      "rating": "防守",
      "sigma": -0.339,
      "degraded": false,
      "html": "daily/2026-01-02/daily-review.html",
      "md_available": false
    }
  ]
}
```

**字段纪律**：

1. **`conclusion` 必须原样透传**，不得在 feed 层重写或摘要——内容层的合规与一致性
   由 `scan_compliance.py` 与 CI 硬阻断保证（`daily-decision-engine` CI 第 2 条）。
   feed 只搬运，不加工。
2. **`rating`/`sigma` 允许为 `null`。** 2026-10-12 的两条 entry 就是
   `rating: null, sigma_source: "missing"`（数据缺口）。客户端**必须显示「数据缺口 · 未评级」**，
   不得回退成中性评级或隐藏该条目。
3. **`degraded: true` 必须显式透传。** 2026-10-16 的 `stock-assistant` 就是降级条目
   （westock-mcp 未连接）。隐藏降级标记等于隐藏数据质量问题。
4. **不含持仓。** feed 里没有任何持仓字段——小程序端不接触个人持仓数据。
5. `summary`/`conclusion` 可能有长度上限要求时，在 `build_site.py` 截断并标 `truncated: true`，
   **不要静默截断**（用户铁律：全量正文无损保留，截断必须显式）。

## 4. 复用边界

### 4.1 能直接复用（零改动）

| 资产 | 复用方式 |
|------|---------|
| **产物数据** | `meta.json` / `entries.json` 直接生成 feed，无需上游改动 |
| **设计 Token** | `design-tokens.json`（10 组：primitive/semantic/typography/space/radius/shape/shadow/layout/meta）—— **这是最有价值的可复用资产**，Taro 侧转成 `theme.ts` 的 design token 映射，颜色/字号/圆角/间距可直接对齐 |
| **视觉语言** | Apple 设计语言规范（`APPLE-DESIGN-SPEC.md` + `ui-design-spec.md`）——大标题、留白、字重层级、克制的分隔，映射到小程序 `rpx` 可高度还原 |
| **评级语义** | 五档评级（进攻/均衡/信号矛盾/防守/回避）+ 色板（红涨绿跌），语义层完全复用 |

### 4.2 不能复用，必须重写（DOM CSS → 小程序）

**核心事实：小程序没有 DOM。** `site_blocks.css`（21.2KB）+ `site_components.css`（10.3KB）
+ `detail-frame.css`（28.7KB）+ `design-tokens.css`（26.2KB）合计 **86.5KB CSS 无法直接使用**。

实测特征命中数（决定重写量的关键证据）：

| 特征 | 命中 | 说明 |
|------|------|------|
| `var(--token)` | **992** | Token 体系庞大，是最大复用资产（可自动转换），也是转换成本来源 |
| `display: grid` | 5 | 不支持，须改写为 flex |
| `backdrop-filter` | 4 | 不支持，毛玻璃效果需重做 |
| `position: sticky` | 1 | 部分支持，行为有差异 |
| `clamp()` | 0 | 未使用，无需处理 |

| 原 CSS 特性 | 小程序映射 | 难度 |
|------------|-----------|------|
| CSS 变量 `var(--token)` | 转 `theme.ts` 常量 + 全局样式类（992 处，**必须脚本化转换**，手改不可行） | 中（有结构化 token，可自动生成） |
| Flexbox | 内联 `display:flex`，**必须逐组件手写**（WXML 无 flex 简写） | 中 |
| Grid（5 处） | **不支持** → 必须改写为 flex 或 `view` 堆叠 | 高 |
| `position: sticky`（1 处） | 部分支持，行为有差异 | 高 |
| `backdrop-filter`（4 处） | 不支持 | 高（毛玻璃效果需重做） |
| 伪元素 `::before/::after` | 仅支持 `::before/::after` 的 `content` | 中 |
| 媒体查询 | 支持，但断点体系需按 rpx 重设计 | 中 |
| 选择器层级（后代/子代） | **仅支持 class/tag/id**，不支持组合器降级 | 高 |
| 原型文件 `apple-prototype.html`（113KB） | 仅作视觉参考，不可复用 | — |

**结论：站点前端的渲染层约 86.5KB CSS 需重写，重写量与「重做一个小程序前端」相当。**
这是 Phase 1 的真实成本，容易被低估。可复用的是**设计语言与 Token**，不是实现代码。

注意 `var()` 的两面性：它既是最大复用资产（992 处 token 引用说明 Token 体系已成体系），
也是转换成本来源。**必须写 token 自动转换脚本**，不能靠人肉改 992 处。

### 4.3 降级策略

三级降级，确保任一层可用：

| 级别 | 方式 | 保真度 |
|------|------|--------|
| L1 优选 | Taro 组件渲染 JSON feed | 中（排版降级，但数据完整） |
| L2 兜底 | `<web-view>` 嵌入 `daily/<date>/index.html` | **高**（原页面原样呈现） |
| L3 离线 | 本地缓存最近 N 天 feed | 低（仅离线查看） |

**L2 是重要的安全网**：即使 L1 排版持续降级，内容永远不会「打不开」，
且零额外维护成本（HTML 已存在）。这大幅降低了 Phase 1 的风险敞口。

## 5. 风险登记

### 5.1 合规（P0 阻断）

#### 5.1.1 金融类目资质 —— 当前形态无法过审

微信官方《非个人主体小程序开放的服务类目》中，金融业相关类目均要求持牌资质：

| 类目 | 资质要求 | 个人主体可得 |
|------|---------|------------|
| 金融业-证券/期货 | 《经营证券期货业务许可证》（经营范围须含证券经纪/承销保荐/自营/商品期货经纪/金融期货经纪之一） | **否** |
| 金融业-证券/期货投资咨询 | 《经营证券期货业务许可证》 | **否** |
| 金融业-公募基金 | 《基金销售业务资格证书》/《基金管理资格证书》/《基金托管业务许可证》等 5 选 1 | **否** |

**关键判断**：当前内容含「Σ 评级（进攻/均衡/防守/回避）+ 偏离幅度 + 触发/失效条件
+ 赔率区间 + 具体操作（挂买单/高抛/定投额度上调）」+ 个人持仓诊断，
**在审核中会被认定为「证券投资咨询服务」**，对应类目要求《经营证券期货业务许可证》。

个人主体与普通商贸公司**无法开通**该类目，无资质提供属平台重点打击范围，
后果是**驳回或封号**。

#### 5.1.2 两条可行路线（需决策）

**路线 A：换类目 + 降级内容形态（推荐）**

- 选择「资讯-财经」或「工具」类目（该类目对个人主体开放）
- **去掉所有操作性表述**：`买入`/`卖出`/`高抛`/`挂单`/`加仓至` 全部移除，
  只保留**事实与评级**
- 去掉赔率区间、触发/失效条件（这三项是最像投顾服务的部分）
- 每屏固定 AI 标识 + 三层免责 + 「不构成投资建议」
- **代价**：内容价值显著下降，从「可操作研判」变成「行情播报」

**路线 B：暂不做小程序，专注站点**

- 站点侧先把合规做扎实（§5.1.3），把内容形态改造成可对外发布
- 小程序延后到有资质时
- **代价**：放弃微信流量入口

**我的判断**：建议 **B**。理由：路线的核心代价是让内容失去实操价值，而研判站的价值
恰恰在于「可操作」。为一个流量入口牺牲核心价值不划算。技术上 Phase 1 的产出
（feed schema、Taro 骨架、Token 映射）**不会浪费**，届时直接接上即可。

#### 5.1.3 无论是否做小程序都必须做的事

内容站本身是对外公开发布的投资研判内容，**当前形态已有合规风险**，
这与小程序无关：

1. 缺少明确的**发布主体与资质说明**
2. **AI 生成内容标识**——需覆盖页面显著位置，不只是文末
3. **三层免责声明**——`disclaimer_profile: investing` 已在 R5 配置中定义，须真正落地
4. **无指令性动词裸奔**——「买入 X」必须改为「若条件 Y 成立，则可考虑 Z」
5. **收益数据披露口径**——若展示历史观点命中率，须说明样本量与局限

**建议动作**：在站点上线前做一次专项合规评审，而不是等到小程序。

### 5.2 域名与备案（P0 技术阻断）

小程序请求域名必须同时满足：**ICP 备案 + HTTPS + 域名级（无端口无路径）+ 每月 50 次修改上限**。

**问题：GitHub Pages 无法作为 request 合法域名。**

| 项 | `*.github.io` 实际情况 | 要求 | 结论 |
|----|---------------------|------|------|
| ICP 备案 | 无法备案（非自有大陆服务器） | 必须 | **不满足** |
| HTTPS | 支持（GitHub 自动签发） | 必须 | 满足 |
| 域名级配置 | 满足 | 必须 | 满足 |
| 稳定性 | 国内访问不稳定，微信网络环境下有失败风险 | 建议 | 不满足 |

**三条可行方案**：

| 方案 | 做法 | 成本 | 评价 |
|------|------|------|------|
| **A 自有备案域名反向代理** | 域名解析到国内服务器，Nginx 反代 GitHub Pages | 域名备案约 10-20 工作日 | 最规范，需备案周期 |
| **B 腾讯云 CloudBase 静态托管** | 站点产物托管到 CloudBase，用平台默认域名 | 最低 | 需注册腾讯云账号 |
| **C 不做 request，改用 web-view** | `web-view` 嵌入网页，避开 request 域名 | 低 | **但 web-view 的业务域名同样要求备案**，规避有限 |

**结论**：无论选哪条，**都必须有一个已 ICP 备案的域名**。这是 Phase 1 的前置条件，
且备案耗时 10-20 工作日，**应立即启动**，与小程序开发并行。

### 5.3 包体积

官方限制（微信开放文档《分包加载》）：

| 项 | 限制 |
|----|------|
| 单个主包 / 单个分包 | ≤ **2M** |
| 全部分包总计 | ≤ **30M**（服务商代开发的小程序 ≤ 20M） |

补充约束：

- **TabBar 页面必须在主包内**，不能拆进分包
- 分包**不能互相嵌套**
- 主包资源可被所有分包引用，**分包 A 的资源不能被分包 B 直接引用**
- 独立分包（`independent: true`）不能依赖主包，`getApp()` 在独立分包内不可用

**Phase 1 预估**：3 页面 + Taro 运行时，**主包约 600KB-1MB**，远低于 2M。
分包在本期非必需，但 `app.json` 的 `subpackages` 结构应**预留**，
Phase 2 加订阅提醒/多页面时无需重构。

另注意：社区广泛引用的「总大小 20M」是**服务商代开发**的小程序限制，
普通小程序是 30M。以官方文档为准。

### 5.4 其他

| 风险 | 等级 | 说明 |
|------|------|------|
| 内容站被搜索引擎收录 | 高 | 个人持仓研判公开可搜索，仓库与 Pages 均建议私有 + 评估收录 |
| feed 缓存时效 | 中 | 微信无强缓存控制，需设计 `generated_at` 兜底与过期提示 |
| 数据缺口展示 | 中 | `rating: null` 条目若被客户端隐藏，等于隐藏数据质量问题（§3.3 第 2 条） |
| 审核周期 | 中 | 类目资质审核 5-7 工作日；被驳回重提更久。建议预留 2-3 周 |
| 免责声明首屏可见性 | 中 | 免责声明若藏在页面底部，用户滑走即不可见；需固定底部条 |

## 6. 分期与验收标准

### Phase 1：只读展示

| 项 | 内容 |
|----|------|
| 范围 | 首页时间线 / 日期页 / 详情页；`web-view` 兜底；离线缓存最近 7 天 |
| 交付 | `build_site.py` 增加 feed 产出 + Taro 工程骨架 + Token 映射 + 3 页面 |
| 前置 | §5.2 备案域名；§5.1 合规路线决策 |

**验收标准（缺一不可）**

1. `feed.json` 与 `entries.json` 逐条对账一致（评级、Σ、结论、时间）
2. `rating: null` 与 `degraded: true` 条目**均可见**且有明确标记
3. 主包体积 ≤ 2M（`开发工具 → 上传` 面板实测）
4. 断网可查看最近 7 天
5. L2 `web-view` 兜底可用
6. 所有页面首屏可见 AI 标识与免责入口
7. **合规路线已决策并落地**（§5.1.2 二选一）
8. iOS / Android / DevTools 三端渲染无阻断性问题

### Phase 2：订阅提醒

| 项 | 内容 |
|----|------|
| 范围 | 订阅消息（`requestSubscribeMessage`）；按评级/数据时点筛选提醒；不新增任何计算 |
| 新增风险 | **订阅消息模板需在 MP 后台申请**，金融类模板可能不开放 |

**验收标准**

1. 每日收盘后按时推送，失败有降级（复用即静默，不反复打扰）
2. 模板申请通过（**这是 Phase 2 的真实前置风险**，建议 Phase 1 期间就去申请探路）
3. 用户可一键关闭；关闭后不再推送
4. 推送内容含 AI 标识与免责
5. 包体积仍 ≤ 2M

### Phase 3：交互

| 项 | 内容 |
|----|------|
| 范围 | 持仓自查（用户本地录入，仅本地计算不上传）、网格价位提醒、图表增强 |
| **强烈建议** | 持仓录入**仅本地存储**，不上传服务器。这既是隐私要求，也是合规要求——客户端出现持仓即强化「投资咨询服务」认定 |

**验收标准**

1. 持仓数据 100% 本地存储，可一键清除，可导出
2. 提醒可配置（评级/价位/时间）
3. 离线可用全部核心功能
4. 通过一次完整合规复审

## 7. 落地建议

1. **先决策 §5.1.2 的合规路线**，再决定是否启动 Phase 1（本文建议 B：暂不做）
2. **立即启动域名备案**（10-20 工作日），无论选哪条路线都用得上
3. `feed.json` 的产出**可以现在就做**——它是纯增量（`build_site.py` 一次 `emit`），
   对站点本身零风险，且同时服务 RSS、H5、外部 API
4. Taro 工程骨架可先行搭建并用 mock 数据开发，与合规决策解耦
5. Phase 2 的订阅消息模板**尽早申请**，它是长周期项，可能直接卡住 Phase 2
