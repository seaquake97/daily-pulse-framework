# ADR-001：六任务共用统一内容契约

## Status

Accepted（2026-10-14）

## Background

项目有 6 个每日定时任务，产出分散在 `/Users/lianghaizhen/WorkBuddy/` 下 6 个目录：

| 任务 | 时点 | 目录 | 主要产出 |
| --- | --- | --- | --- |
| 股票助手 | 9:28 | `股票助手/` | stock_assistant.md/html + market_data.json + viewpoint.json |
| 基金每日盘面分析 | 11:00 | `基金每日盘面分析（11:00）/` | fund_market_analysis.md/html |
| 基金每日操作指引 | 14:30 | `基金每日操作指引（14:30）/` | fund_operation_guide.md + market_data.json |
| 股票复盘 | 15:05 | `股票复盘/` | stock_review.md + viewpoint.json |
| 每日总复盘 | 15:30 | `每日总复盘（15:30）/` | daily_review.html + market_data.json |
| v2 决策引擎 | 15:31 | `每日基金股票复盘-v2决策引擎/` | 当前为空目录（archive 为空） |

问题：每个任务的 prompt 与写作习惯各自演化，产出结构互不对齐。2026-10-14 实测确认的偏差：

- **章节编号四套并存**：纯中文数字（股票助手 `一、二、三`）、中文数字带多余空格（11:00 盘面 `## 一、 全场 A 股动态行情家数与结构统计`）、emoji 前缀加中文数字（14:30 指引 8 个章节标题各带一个 emoji，码点见 ADR-003 证据表）、两位阿拉伯数字加英文小节（15:05 复盘 `## 01 结论卡`、`### YOU ASKED`）
- **行数落差巨大**：9:28 产出 73 行，15:05 产出 144 行，同一项目内两倍差距，且无统一裁剪规则
- **同一概念四种叫法**：信号明细被称作「六信号明细」「六维确定性信号硬校验结果」「四层信号矩阵」「信号面」
- **数据链断裂**：11:00 盘面无 `market_data.json`，其 Σ 值无法回溯校验
- **时点字段未声明**：三份 `market_data.json` 均缺 `snapshot_at`；`data_stage` 已实际写入但不在 schema 的 `properties` 与 `required` 中，属未声明字段

后果：读者横向对比任意两份报告都需要人工翻译章节名；机器无法解析产出结构；`daily-decision-engine` 技能里定义的「决策卡七件套」「六维信号」等规范无法跨任务落地，因为每个任务都自造了一套近似结构。

约束条件：产出必须保持研判深度，不能为了统一格式牺牲分析内容；同时不能引入第三方依赖倒逼重装环境。

## Decision

建立一份**自包含的内容契约**，作为六任务结构的唯一来源，由代码实现并可机器校验。

具体决策：

1. **统一章节骨架**：16 个章节构成全集，其中 3 个必选（结论卡、待验证信号、免责声明），其余按任务选入。骨架由 `content_contract.SECTIONS` 唯一定义，生成侧调用 `build_skeleton(slug)` 取子集，**顺序恒为声明顺序**。

2. **结构差异由「章节有无」吸收，不由「章节命名」吸收**。这是应对 73 行与 144 行落差的核心设计：
   - 条件章节当日无数据时**保留章节标题**，正文写明「本时点无数据」及原因。禁止删除——删除会让当日结构与次日不可比，读者失去横向对照基准。
   - 章节内长度自由。9:28 的持仓动作卡可以只有 9 行，15:30 的专家圆桌可以写满 6 位专家。骨架约束「有哪些维度」，不约束「每个维度写多长」。

3. **唯一编号体系**：两位阿拉伯数字加半角句点（`## 01. 结论卡`）。废弃中文数字、单位数字、三位数字。

4. **统一维度词典**：18 个维度各有唯一规范中文名与英文名。45 条废弃写法列入 `BANNED_DIMENSIONS`，出现即判违规。废弃名单全部来自真实产出扫描，不凭空设想。

5. **校验由代码执行，不依赖人工通读**：`validate_contract()` 返回结构化违规清单（规则名、行号、消息、级别），可直接接入发布流程做阻断。

6. **零第三方依赖**：纯标准库，Python 3.13（项目 `MANAGED_PY` 实际版本）。

## Consequences

正面：

- 章节名、编号、维度名在全项目唯一，横向对比不再需要人工翻译
- 结构可被机器解析，为后续自动化处理（跨任务观点比对、异常检测）打开可能
- 违规可被门禁拦截，不依赖执行者的自觉
- 骨架与校验分离：新增任务只需在 `applies_to` 加 slug，无需改校验逻辑

负面：

- 历史产出不合规。本契约从生效日向后适用，不回溯整改，切换期存在「新旧混排」
- 新增维度需同时改代码词表与规范文档两处，存在漂移风险（已用「新增维度必须两处同步更新」的硬约束缓解）
- 骨架对任务是约束而非自由，个别任务可能觉得受限

中性：

- 校验器初期会产生较多违规告警（当日四份产出共 86 条 error），这是真实存量问题的暴露，不是误报

## Alternatives Considered

**方案 A：只统一章节标题文本，不约束编号与维度名。**
改动最小，但 15:05 复盘已用 `## 01 结论卡`、股票助手用 `## 一、结论卡`，只统一文本仍留下两套编号。并被否决。

**方案 B：各任务保留自有结构，增加一份总索引做映射。**
不改动既有产出，但读者仍需跳转映射表才能对齐，「前后一致性高」的用户诉求未解决。并被否决。

**方案 C：引入文档即代码工具链（如 Markdown 校验框架）。**
能力更强，但引入依赖与配置成本，与项目「零依赖、直接可跑」的现状不匹配。并被否决。

**方案 D：只靠 prompt 约束，不写校验代码。**
无法防回归。`daily-decision-engine` 技能已用 prompt 方式约束「决策卡七件套」，实际产出中 14:30 指引的决策卡确实规范，但 15:05 复盘与 11:00 盘面并未遵循——说明纯 prompt 约束在多任务场景下不可靠。并被否决。
