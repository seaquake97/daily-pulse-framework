# ADR-005: 15:05 与 15:30 两任务的产物归属与发布层取数

## Status: Accepted (2026-10-16)

## Background

PM 在 GAP-PM 清单中提出：站点上 `stock-review`（15:05 股票复盘）与
`daily-review`（15:30 每日总复盘）两个 slug 可能给用户看同一份内容，
违反 PRODUCT-CONTRACT §1.1 定义的两个层级（15:05 答「哪条错了、为什么」，
15:30 答「五场信哪场、明天看什么」）。要求架构裁决。

本 ADR 的事实基础全部来自实测，不采信任何一方的推演。

## 实测事实

### 事实一：`stock_review.md` 在两个目录间逐字节相同

```
2026-10-13  15:05=c1b6592d(9934B)   15:30=c1b6592d(9934B)    IDENTICAL
2026-10-14  15:05=33e2b958(11097B)  15:30=33e2b958(11097B)   IDENTICAL
2026-10-15  15:05=5c88ae87(14120B)  15:30=5c88ae87(14120B)   IDENTICAL
2026-10-16  15:05 无 md             15:30 有 md
```

PM 提供的 MD5 证据成立。`publish_to_github.py:86` 的注释
「总复盘的 md 即 stock_review.md（与股票复盘同文件，MD5 相同）」
是**准确的事实描述**，不是托词。

### 事实二：两个 slug 的页面内容**并不相同**（与 PM 的判断相反）

```
2026-10-14  stock-review 正文 4841 字符  quick_ratio 0.774
            daily-review 正文 6104 字符
2026-10-15  stock-review 正文 6225 字符  quick_ratio 0.812
            daily-review 正文 6838 字符
```

根因在 `publish_to_github.py:80-88` 的 `TASK_SOURCES`：

| slug | 任务目录 | 候选文件 | 实际发布内容 |
|---|---|---|---|
| `stock-review` | 股票复盘（15:05） | `stock_review.md` / `.html` | md 经 `render_md.py` 渲染 |
| `daily-review` | 每日总复盘（15:30） | `daily_review.html` | **上游独立 HTML** |

两者读的是**不同目录的不同文件**：`daily-review` 读 `daily_review.html`
（52937B，15:30 目录），`stock-review` 读 `stock_review.md`（13757B）。
15:30 目录里同时存在这两个文件，它们不是同一个东西。

因此「站点展示同一份内容、给出同一个结论」**不成立**。
相似度 0.77-0.81 说明二者同源（都基于当日行情），但呈现层与章节结构不同。

### 事实三：`settlement.json` 未被发布层读取，但其内容已在正文（2026-10-16 修订）

15:30 的 `settlement.json` 是 `settle_viewpoints.py` 的输出
（`status: settled`、`hits: 1/2`、`hit_rate: 50%`、逐条 viewpoint 明细）。

**原表述「它既不在 stock_review.md 的章节里，也不在 daily_review.html 里」是错的。**
PM 指出后实测确认：`stock_review.md` 的 **06 章就是结算**，且已带命中率与逐条判定：

```
## 06 昨日观点兑现（Viewpoint Settlement）
- V1 观点（两市成交额维持在1.5万亿以上且沪指守稳3680点支撑）：TRIGGERED（命中），
  今日实际成交额 15,692.32 亿元，满足 >= 15,000.0 亿元条件
- V2 观点（若沪指击穿3680点或两市成交跌破1.4万亿）：NOT_TRIGGERED（未触发）
- 昨日结算统计：命中 1/2，命中率 50%，条件未触发 1 项，无法评估 0 项
```

且该章已渲染进 `_stage/docs/daily/2026-10-15/stock-review.html`。

**准确表述**：`settlement.json` 作为**数据源**从未被发布层读取
（`TASK_SOURCES` 无此候选文件），但其内容**已由引擎写进 md 正文**。
所以新增 slug 的价值是「结构化呈现 + 可机检」，**不是「首次可见」**。
本 ADR 初稿把「未被发布层读取」误写成「从未可见」，据此把方案定位为
「让 15:05 核心问题有真实数据来源」，属于对现状的过度描述，已更正。

原判断中成立的部分：契约 §1.1 给 15:05 定的核心问题「哪条错了、为什么」，
其数据在正文里是**叙述式**的（自然语言句子），无法被 `feed.json` 消费、
无法被校验器检查、无法在页面上形成可比对的结构。这仍是真实缺口，
只是缺口的性质是「结构化」而非「可见性」。

### 事实三之二：`settlement.json` 覆盖率仅 2/10（PM 实测，我复核）

```
09-17 ~ 09-24   settlement.json 无
10-12 no   10-13 no   10-14 no（viewpoint.json 有）
10-15 YES  10-16 YES
```

15:05 目录同构（10-15/10-16 有，其余无）。这直接否决了「把 settlement
作为常规候选文件」的默认写法——见决策二的前置条件。

生成机制实测：任务目录无脚本引用 `settlement`，`run_pipeline.py` 也无
settle stage。**`settlement.json` 目前靠人肉调用 `settle_viewpoints.py` 生成**，
这解释了覆盖率为何断续（A-14 的接线工作）。

### 事实三之三：正文泄漏本机绝对路径（PM 实测，我复核）

`_stage/docs/daily/2026-10-15/stock-review.html:1939` 与同名 `.md` 渲染出：

```
依据 /Users/lianghaizhen/WorkBuddy/股票复盘/2026-10-15/settlement.json 自动结算结果
```

这是 GitHub Pages 公开站点上的本机用户名与目录结构泄漏。
与新增 slug 直接相关：做 settlement 发布会直接读到这行硬编码路径。
处置见待办 A-22。

### 事实四：15:30 目录才是可靠来源

15:05 目录近 4 日仅 10-15 有完整 7 文件产物，10-16 只有 5 个 JSON、
无 md 无 html，10-12 目录为空。15:30 目录每日均有 `stock_review.md`
+ `daily_review.html`。

## Decision

### 决策一：`TASK_SOURCES["stock-review"]` 改指 15:30 目录

```python
"stock-review": ("每日总复盘（15:30）", ["stock_review.md"]),
"daily-review": ("每日总复盘（15:30）", ["daily_review.html"]),
```

两个 slug 读同一目录但不同文件，md 与 html 各归其位。
15:05 目录降级为「可选副本」，不再作为发布来源。

理由：15:30 目录的产物完整性实测更高（事实四），且它同时持有
md 与 html 两种形态，能满足 `render_md.py` 统一渲染管线的要求。

**注意**：这使两个 slug 同源同目录，必须配合决策三的显式标注。

### 决策二：撤回「两 slug 内容雷同」的判断；新增 `settlement` 但定位为「结构化」

PM 提出的决策 2（B 方案：让 15:05 输出结算、15:30 输出横向对比）
**方向正确但前提不成立**——两 slug 读的是不同文件、呈现不同章节，
不是同一份内容（事实二）。按 B 重构会去修一个不存在的问题。

真实缺口是事实三：**结算数据在正文里是叙述式的，无法被机检**。

**因此决策二改为**：新增发布物 `settlement`，而非重构两个 slug 的内容分工。

| 项 | 值 |
|---|---|
| slug | `settlement` |
| 源 | `15:30 目录 / settlement.json`（15:05 目录同源副本，MD5 相同，见 A-20） |
| 呈现 | 由 `render_md.py` 从 JSON 生成章节：命中率 + 逐条 viewpoint 兑现状态 |
| 定位 | **结构化呈现 + 可机检**，不是「首次可见」——正文已有叙述版（见事实三修订） |
| 时点 | **09:28**（裁决见下） |

#### 时点裁决：09:28 而非 15:05

PM 提出这个语义矛盾，我复核后采纳他的判断：

- `settlement.json` 的 `ledger_date` 指向**昨日**（10-16 的文件 `ledger_date: 2026-10-15`）
- 物理位置在 15:30 目录，但逻辑内容是「昨天那几条观点对不对」
- 用户在 09:28 开盘前拿到昨日兑现情况，才能决定「今天该不该信自己的判断」

**放在 15:05 意味着用户要等收盘后才知道昨天的观点对错**，与产品价值相悖。
因此时点定为 **09:28**，与 `stock-assistant` 同格、排在最前。

**副作用裁决**：日期页时间线从 4 格变 5 格（09:28 两格、11:00、14:30、15:30）。
需复核 `test_conclusion_contract.py` 与 `site_pages.py` 的条目数假设。
这是可接受的——多一格早间信息，比把早间该看的信息压到收盘后更符合读者利益。

**与决策三的关系**：`stock-review` 与 `daily-review` 同源（15:30 目录），
`settlement` 不参与该同源关系（它读的是 json 而非报告），故不加 `same_source` 标注。

**排序冲突裁决**：`settlement` 时点定为 **09:28**（PM 提出、架构师采纳）。
它与 `stock-assistant` 同格，按 `TASK_SOURCES` 插入序排在最前。
这消除了与 `stock-review` 的排序冲突。

采纳 PM 的理由：结算的内容是「昨日观点对不对」（`ledger_date` 指向昨日），
开盘前拿到它才能决定今天信不信自己的判断。放在 15:05 收盘后是延迟消费。

若后续产品判断改变，改 `TASK_META` 一处即可，不影响其他决策。

**前置条件一（实测发现，必须先做）**：`settlement.json` **没有任何 schema 或校验器**。

- `framework/engine/collect/` 与 `framework/engine/report/` 下无任何 `settlement` 引用
- 结构实测：`status` / `today` / `ledger_date` / `counts` / `hits` / `evaluable` /
  `hit_rate` / `by_type` / `viewpoints[]`，单条 viewpoint 含
  `id` / `claim` / `type` / `condition` / `action` / `eval_at` / `status` / `settle_detail`
- 生产方是 `settle_viewpoints.py`，其 docstring 只描述了 `viewpoint.json`
  的 `status: pending` 状态，未声明 `settlement.json` 的输出契约
- **PM 实测补充**：`settlement.json` 在 15:05 与 15:30 两个目录都有且 MD5 相同
  （`a4485a06e4e38aff0ac2c2bc2538e6ec`）。schema 需覆盖这个同源副本事实

把一个无契约的 JSON 直接接进发布层，等于把上游格式变更变成线上渲染故障。
因此**先补 `settlement.schema.json` + 校验器（并入 A-09 的 collect 批次），
再接发布层**。这与 `market_data.json` 当初的做法一致——
它也是先有 schema（基于 22 份真实产物统计）才接进管线的。

**前置条件二（覆盖率约束，PM 实测我复核）**：`settlement.json` 覆盖率仅 **2/10**。

若按常规候选文件写 `["settlement.json"]`，则 8/10 的日期页会多出一个
「当日未产出」占位卡——**比现在更糟**，等于把 PM-05 的问题从 1 个任务
扩散到 6 个任务。

**因此 `settlement` 必须走「无需结算」语义：缺数据时整卡不出现，
而非出占位。** 语义依据：没有昨日观点台账就没有结算，
这不是「结算任务失败」。这要求在决策四的缺失语义中新增第四种（见下）。

**前置条件三**：新 slug 会使日期页时间线从 4 格增至 5 格（09:28 两格）。
需复核 `test_conclusion_contract.py` 与 `site_pages.py:32,87` 的条目数假设。


### 决策二之二：`settle_viewpoints.py` 迁移时需带出契约

A-09 把引擎脚本迁入 `framework/engine/signals/` 时，`settle_viewpoints.py`
需同时产出 `settlement.schema.json`，否则迁移后仍是无契约 JSON。

### 决策三：同源 slug 必须在时间线显式标注

无论决策二如何演化，`stock-review` 与 `daily-review` 现在同源同目录，
时间线必须显式说明二者关系，避免用户把一次研判数成两次。

实现：`TASK_META` 增 `same_source` 字段标注同源关系，
`site_render.py` 时间线卡片渲染「同上源」提示。

**这一条是决策一的必要配套**，不做就是欺骗读者。

### 决策四：区分四种缺失语义（PM 补第三种，我补第四种）

PM 区分了「未运行」与「运行但无产出」。实测发现第三种已由 PM 侧正确处理，
而 `settlement` 的覆盖率约束暴露出**第四种**，此前无人区分：

| 情形 | 判定 | 发布层行为 | 渲染层行为 | 现状 |
|---|---|---|---|---|
| 1. 任务目录不存在 | 未运行 | 退出码 2 + 告警 | 不出卡片 | 静默少一格 |
| 2. 目录存在但候选文件全缺 | 运行但无产出 | 退出码 2 + 告警 | 出卡片 + 标注「当日未产出」 | 静默少一格 |
| 3. 产物在但数据源降级 | 已产出但不可信 | 正常发布 | `tag gap` 降级标注 | **已正确处理** |
| 4. 该任务本就不必产出 | 无需产出 | 正常发布 | **整卡不出现** | 无此语义 |

**第四种是 `settlement` 专属的**：覆盖率 2/10，没有昨日观点台账就没有结算，
这不是「结算失败」。若复用第二种语义，会在 8/10 的日期页上放一个
「结算未产出」的占位卡——把一个可选项变成每日噪声。

因此 `TASK_SOURCES` 需支持**可选任务**标记（`optional: True`），
`collect()` 遇到 optional 任务缺文件时静默跳过且不算缺失。

这是 A-03 的完整规格（含 PM-05 的发布层一端），四条合并处理。

## Consequences

正面：
- 10-16 的缺条目事故不再复现（决策一）。
- 结算数据首次以**结构化**形式上线，可被 `feed.json` 消费、可被校验器检查；
  正文原有的叙述版保留，两相印证（决策二）。
- 结算在 09:28 开盘前可见，读者当天就能校准对自身判断的信心（决策二时点裁决）。
- 四种缺失语义分开，未运行/无产出/降级/无需产出各有各的表现（决策四）。
- 站点不再泄漏本机绝对路径（A-22）。

负面：
- `TASK_SOURCES` 改动会让 15:05 目录彻底失去**发布**用途。
- 新增 `settlement` slug 使时间线当天的条目数从 4 增至 5，且 8/10 日期为 4 格
  （settlement 不出现）——**同一天里不同日期的格数不一致**，
  需复核 `site_pages.py` 与 `test_conclusion_contract.py` 的相关假设。

### 15:05 停产 `stock_review.md`：采纳，但顺序不能反

PM 决策「停 15:05 的 md 产出、保留 JSON」，我采纳，并补一条他指出的顺序约束。

PM 给出的理由比我原提的「纯浪费 + 制造歧义」更硬：md 正文里写着
「依据 `/Users/lianghaizhen/WorkBuddy/股票复盘/<date>/settlement.json`」，
引用的是 **15:05 目录**；而决策一实施后 md 源在 15:30 目录。
若先停 15:05 产出，会变成「源在 15:30、引用指向 15:05」——读者或下游
照该路径取数会取不到。**从「内容雷同」变成「引用失效」，后者更隐蔽。**

因此**执行顺序必须为**：

1. 先修 md 里的绝对路径引用（A-22，改为中性表述如「依据引擎自动结算结果」）
2. 再停 15:05 的 `stock_review.md` 产出
3. 15:05 保留 JSON 产出（`holdings.json` / `market_data.json` /
   `viewpoint.json` / `settlement.json`）——这些是数据源，停 md 不停 JSON

15:05 的产品定位相应明确为**数据与观点生产时点**，不是发布时点。
`TASK_META` 中 `stock-review` 的 blurb 当前是「竞价窗口的持仓级研判与条件单建议」，
停产 md 后需与该定位对齐。

### A-22 的实现落点：sanitizer 新增 `path_pass`

修在**渲染层**而非上游 md，理由有三：

1. 上游 md 是 5 个任务共用的产物格式，改它要动引擎与任务书；
   而泄漏发生在**发布**这一刻，发布层是唯一必经之路
2. 与 emoji / 渐变 / 裸 hex 的处置纪律一致——它们都在 sanitizer 里做，
   路径泄漏是同一类问题（产物里的实现细节不该出现在读者面前）
3. 上游若再引入新的路径引用（明天可能是 `holdings.json` 的路径），
   渲染层的规则自动覆盖，无需回到上游加规则

实现：`sanitizer/path_pass.py`，仿 `script_pass.py` 的单一职责模式，
在 `core.py:62-68` 的 pass 链中插入（建议排在 `script_pass` 之后、
`gradient_pass` 之前——路径泄漏是文本内容问题，与样式层无关）。

规则：匹配 `/Users/<name>/...` 与 `~/...` 形式的绝对路径，替换为中性表述。
`report` 需记 `path-redacted` 计数，进 `manifest.sanitize_warn_reasons`（A-11），
使这类修复可追溯——避免「静默脱敏」变成另一种沉默。
